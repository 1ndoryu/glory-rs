## 256A-2 — Reporte de verificación sync + documentación

- **Que:** Implementar `generarReporteSync()` que recolecta estado de todos los subsistemas de sync (auth, config, backend, tracking, uploadQueue, journal, circuitBreaker) y genera auto-diagnósticos. Expuesto como `window.__KAMPLES_SYNC_REPORT__()` en ambas ventanas Tauri.
- **Archivos:**
  - `clients/desktop/src/services/syncService.ts` — +`SyncReport` interface, +`generarReporteSync()` (~280 líneas), +`sentinel-disable-file` (fachada pública)
  - `clients/desktop/src/global.d.ts` — +`__KAMPLES_SYNC_REPORT__` en Window
  - `clients/desktop/src/sync.tsx` — import + expose en window globals
  - `clients/desktop/src/main.tsx` — import + expose en window globals
  - `Agente/documentacion/sync/sync-desktop-estado-2026-06-24.md` — sección 4.4 agregada, historial actualizado, resumen actualizado
  - `roadmap.md` — 256A-2 como completada
- **Gotchas:**
  - `syncService.ts` es una fachada que centraliza ~30 re-exportaciones; excede 400 líneas por diseño (sentinel-disable-file justificado)
  - `generarReporteSync()` usa dynamic imports (`import()`) para los subsistemas que no se cargan al inicio (tracking, upload queue, journal, circuit breaker) — así no fuerza loading temprano de esos módulos
  - La función intenta leer `GLORY_CONTEXT` primero, y si no está disponible (ventana sync que no carga el SPA React), fallback a Tauri Store `auth.json`
  - El backend check usa `fetch` con `AbortController` (5s timeout) para no colgarse si el servidor no responde
- **Sentinel:** No aplica
- **GLORY:** No aplica (específico del proyecto)
