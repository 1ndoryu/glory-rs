## 265A-1 — Activar burst dinámico de CPU para hostings Coolify
- **Que:** se implementó el primer slice operativo del plan de límites dinámicos. Un nuevo loop background lee snapshots recientes de infraestructura, detecta hostings Coolify que están pegando contra su cap actual y ajusta en caliente `docker update --cpus` sobre el contenedor principal (`site` o `wordpress`). Cuando sube la presión del host o baja la demanda, el loop restaura el baseline contractual del plan.
- **Archivos:** `src/services/cpu_burst.rs`, `src/repositories/infrastructure.rs`, `src/repositories/mod.rs`, `src/services/mod.rs`, `src/main.rs`, `roadmap.md`, `Agente/lecciones/lecciones-aprendidas.md`, `Agente/planes/plan-recursos-hosting-2026-05-22.md`, `Agente/documentacion/hosting/limites-dinamicos-hosting-2026-05-25.md`, `Agente/completados/tareas-2026-05-26.md`
- **Gotchas:** el target real no sale del plan sino de la identidad runtime persistida (`deployment_uuid` con fallback a `coolify_site_name`) más el servicio efectivo del compose. Mientras no exista una tabla propia de overrides, el loop tiene que reconciliarse contra el límite runtime observado por el sampler para no repetir el mismo `docker update` en cada ciclo.

## 265A-2 — Corregir lectura de límites runtime para burst en hostings legacy
- **Que:** se corrigió el parser del sampler para aceptar los `\t` literales que devuelve `docker inspect --format`, lo que impedía persistir `site_cpu_limit_cores` y dejaba al burst dinámico ciego en hostings existentes. La validación de campo se centró en `hosting-0fa1d5da`, donde Docker exponía límites reales pero la BD guardaba `null`.
- **Archivos:** `src/services/infrastructure_metrics.rs`, `roadmap.md`, `Agente/lecciones/lecciones-aprendidas.md`, `Agente/planes/plan-recursos-hosting-2026-05-22.md`, `Agente/completados/tareas-2026-05-26.md`
- **Gotchas:** `docker stats` sí entrega tabs reales, pero `docker inspect --format '{{...}}\t{{...}}'` no; mezcla un tab real con separadores escapados. Si el parser solo divide por `\t` reales, todos los límites runtime quedan en `null` aunque Docker tenga caps correctos.
- **Sentinel:** No aplica
- **GLORY:** No aplica

## 265A-3 — Corregir executor real del cpu burst en hostings legacy
- **Que:** la prueba de campo en `hosting-0fa1d5da` demostró que el burst sí veía al sitio como `demander`, pero nunca encontraba el contenedor porque estaba resolviendo `docker compose -p hosting-0fa1d5da ...` cuando el `com.docker.compose.project` real era `v77j8dfkb8rat8mlhzoid2eh`. Se corrigió `cpu_burst.rs` para probar primero `deployment_uuid`, dejar `coolify_site_name` solo como fallback y no congelar `last_requested_target` si el apply falla.
- **Archivos:** `src/services/cpu_burst.rs`, `roadmap.md`, `Agente/lecciones/lecciones-aprendidas.md`, `Agente/planes/plan-recursos-hosting-2026-05-22.md`, `Agente/documentacion/hosting/limites-dinamicos-hosting-2026-05-25.md`, `Agente/completados/tareas-2026-05-26.md`
- **Gotchas:** en Coolify el nombre comercial del sitio no siempre coincide con `com.docker.compose.project`; para acciones runtime (`docker compose -p`, `docker update`, `ps -q`) el identificador operativo confiable es `deployment_uuid`. Además, si un apply falla y el loop memoriza igual el target pedido, deja de reintentar aunque el contenedor siga en baseline.

## 265A-5 — Añadir throttling CPU solo bajo contención seleccionable por plan
- **Que:** se agregó `cpu_scaling_policy` a `hosting_plan_configs` para elegir entre el modelo previo `baseline_burst` y el nuevo `contention_throttle`. El nuevo default deja el hosting sin cap fuera de contención y solo aplica un límite temporal cuando la VPS entra en presión alta; el loop registra eventos específicos y el sampler ya reconoce `cpu_quota=-1` como runtime ilimitado aunque Docker conserve `NanoCpus` viejo.
- **Archivos:** `src/models/hosting/entities.rs`, `src/models/hosting/mod.rs`, `src/models/mod.rs`, `src/models/hosting/requests.rs`, `src/repositories/hosting.rs`, `src/repositories/infrastructure.rs`, `src/services/cpu_burst.rs`, `src/services/infrastructure_metrics.rs`, `src/handlers/hosting/plans.rs`, `src/services/coolify.rs`, `migrations/20260526000000_hosting_cpu_scaling_policy.up.sql`, `migrations/20260526000000_hosting_cpu_scaling_policy.down.sql`, `roadmap.md`, `Agente/planes/plan-recursos-hosting-2026-05-22.md`, `Agente/documentacion/hosting/limites-dinamicos-hosting-2026-05-25.md`, `Agente/lecciones/lecciones-aprendidas.md`, `Agente/completados/tareas-2026-05-26.md`
- **Gotchas:** `docker update --cpus 0` no quita el límite; el mecanismo real es `docker update --cpu-quota -1`. Aun así, `docker inspect` deja `HostConfig.NanoCpus` stale, así que el sampler debe tratar `CpuQuota < 0` como la señal de ilimitado o el backend seguirá pensando que el sitio está capado a su baseline.
- **Sentinel:** No aplica
- **GLORY:** No aplica
